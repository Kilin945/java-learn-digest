📘 每週回顧 · Java / Spring Boot · 2026-07-17

這週我們把 Profiles（dev/prod 設定切換）和 @SpringBootApplication 自動組態原理串起來了，來做個主動回想（active recall）複習一下～

🧠 本週回想題

  1. application.properties 和 application-dev.properties 這兩個設定檔，各自的角色與生效時機有什麼不同？
  2. 要啟用某個 profile，有哪兩種常見方式可以設定 spring.profiles.active？
  3. 如果共用設定檔和 dev 專屬設定檔對同一個設定項目寫了不同的值，最後會以哪個為準？為什麼？
  4. 假設你有一個「寄信」功能介面，要讓 dev 環境用假的寄信元件、prod 環境用真的寄信元件，你會怎麼用 @Profile 設計？
  5. 為什麼正式（prod）環境通常不會把 profile 直接寫死在設定檔裡，而是用 SPRING_PROFILES_ACTIVE 環境變數來啟用？這樣做的好處是什麼？
  6. 如果想同時啟用 dev 和 mail 兩個 profile，設定值該怎麼寫？
  7. @SpringBootApplication 其實是哪三個註解打包而成的？各自負責什麼工作？
  8. Spring Boot 的自動組態（@EnableAutoConfiguration）是怎麼判斷「該不該」幫你自動套用某個功能的設定（例如網頁相關的設定）？和 @ConditionalOnClass 有什麼關係？

—— 解答 ——

  1. application.properties 是預設、所有環境都會套用的共用設定；application-dev.properties 是只有啟用 dev 這個 profile 時才會額外生效的專屬設定。
  2. 一種是直接寫在 application.properties 裡的 spring.profiles.active=dev，另一種是啟動時用命令列參數 --spring.profiles.active=xxx 覆蓋（override）。
  3. 以專屬設定檔（如 application-dev.properties）為準，因為 Spring Boot 會把共用設定和專屬設定「疊加（layer）」，同名項目由專屬設定覆蓋共用設定。
  4. 在該功能介面的兩個實作類別上分別加 @Profile("dev")（假的寄信元件）和 @Profile("prod")（真的寄信元件），Spring 會依目前啟用的 profile 自動組裝正確的實作，呼叫端程式碼完全不用改。
  5. 因為同一份 jar 檔要能部署到不同機器、變成不同環境，用環境變數在「部署當下」決定 profile，比把設定寫死在檔案裡更有彈性，也不用為了換環境重新打包或改程式碼。
  6. 用逗號分隔即可，例如 SPRING_PROFILES_ACTIVE=dev,mail，可以同時啟用多個 profile。
  7. 是 @SpringBootConfiguration（宣告這是一個設定類別）、@EnableAutoConfiguration（開啟自動組態機制）、@ComponentScan（掃描並註冊元件）三個打包成的懶人包（convenience annotation）。
  8. 自動組態會用 @ConditionalOnClass 檢查 classpath 上有沒有特定類別存在（例如專案有沒有加 spring-boot-starter-web 這個 starter 依賴），有偵測到相關類別才會觸發對應的自動設定；沒有的話該組態就不會生效，避免多餘或錯誤的設定被套用。
