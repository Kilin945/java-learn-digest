—— 解答 ——

A1 · Bean 基礎

IoC 容器負責建立與管理物件的生命週期及依賴關係，讓你不需要手動 new，控制權從程式碼轉交給框架（故稱「控制反轉」）。
Bean 就是被 IoC 容器管理的 Java 物件。
在 class 上標 @Component，Spring 啟動時的 Component Scan 就會掃描到它，自動建立實例並存入容器。

A2 · Annotation 職責

@Service → 業務邏輯層（處理商業規則）
@Repository → 資料存取層（執行 CRUD）
@Repository 額外提供「持久層例外轉換（Exception Translation）」：JDBC / JPA 拋出的底層例外會被自動轉換為 Spring 統一的 DataAccessException，讓例外處理更一致。

A3 · 三層架構

Controller (@RestController) → 接收 HTTP 請求，轉發給 Service
Service (@Service) → 處理業務邏輯，協調多個 Repository
Repository (@Repository) → 與資料庫互動，執行 CRUD

三層分離的好處：修改任一層（例如換資料庫）不影響其他層，職責一目了然。

A4 · 欄位注入的缺點

① 不可標 final：欄位不能設為 final，依賴在執行期可被替換，缺乏不可變保障。
② 測試困難：不透過 Spring 容器就無法注入，單元測試必須動用 Reflection 才能塞入 mock。
③ 隱藏依賴：從 class 外部（建構子簽名）看不出它需要哪些依賴，破壞了「依賴明確可見」的設計原則。

A5 · 建構子注入的優勢

建構子注入讓所有必要依賴透過建構子參數傳入，搭配 final 欄位可確保依賴一旦設定後不可被修改（不可變性）。
在測試時，只需直接 new MyService(mockRepo) 即可注入 mock，完全不需要啟動 Spring 容器，測試速度快且可靠。

A6 · Spring 4.3+ 的語法簡化

當 class 只有唯一一個建構子時，可以省略 @Autowired，Spring 會自動辨識並執行注入。
Lombok 的 @RequiredArgsConstructor 會為所有 final 欄位自動生成唯一建構子，加上 Spring 4.3+ 的這個規則，兩者合用就是現代 Spring 最簡潔的 DI 寫法，完全不需要手寫建構子或 @Autowired。

A7 · Setter 注入的適用場景

① 可選依賴：某 Bean 不一定存在（例如通知服務可能未部署）。用 @Autowired(required=false) 標在 setter 上，找不到對應 Bean 時欄位保持 null 而不拋例外。若省略 required=false，找不到 Bean 時 Spring 啟動就會直接失敗。
② 循環依賴：A 依賴 B、B 依賴 A 時，建構子注入會讓容器卡死，改用 setter 注入可讓 Spring 先建立實例再填入依賴，打破循環。

A8 · 綜合應用

必要依賴 → 建構子注入（搭配 final）；可選依賴 → setter 注入（搭配 required=false）： 

@Service
public class OrderService {

    // 必要依賴：final 保證不可變
    private final OrderRepository orderRepo;

    // 可選依賴：非 final，可能為 null
    private NotificationService notificationSvc;

    // 建構子注入（Spring 4.3+ 可省略 @Autowired）
    public OrderService(OrderRepository orderRepo) {
        this.orderRepo = orderRepo;
    }

    // Setter 注入（可選依賴）
    @Autowired(required = false)
    public void setNotificationService(NotificationService svc) {
        this.notificationSvc = svc;
    }
}

使用前記得 null-check：if (notificationSvc != null) { notificationSvc.send(...); }
