Q7 ／ 第三方 Bean 登記

Jackson 的 ObjectMapper 是第三方 class，你無法在它的原始碼上加 @Component。
請說明如何把它注冊成 Spring Bean，讓其他元件可以透過建構子注入使用它。

—— 解答 ——

A1

直接 new 會造成緊耦合（tight coupling）：呼叫方與具體實作綁死，換依賴時必須修改呼叫方；撰寫單元測試時也無法輕易替換成假的（mock）實作。

Spring IoC 把物件建立的控制權「反轉」給框架：由 IoC 容器統一建立、管理所有 Bean，再主動把依賴「注入」給需要的地方——呼叫方只宣告「我需要什麼」，不關心「由誰建立」。

A2

三者都是 @Component 的語意化別名（stereotype annotation），功能上等價於 @Component，都會讓 Spring 掃描並建立 Bean。差別在語意與分層：

  • @RestController：控制層，接收 HTTP 請求、回傳 JSON
  • @Service：業務邏輯層，放核心流程
  • @Repository：資料存取層，與資料庫互動

A3

版本 B 是建構子注入，也是推薦做法。原因：

  • 欄位可宣告 final，確保注入後不被修改（不可變性）
  • 依賴在建構時就必須提供，物件一建立就處於完整狀態
  • 單元測試時直接 new OrderService(mockPayment) 即可，不需要 Spring 容器
  • 版本 A 的 field injection 依賴反射，且欄位無法宣告 final

A4

應該依賴介面（inject the interface），而非具體實作。這樣：

  • 呼叫方（Controller）只知道「它能做什麼」，不知道「誰在做」
  • 替換實作（例如從 Email 通知改成 SMS 通知）時，Controller 一行程式碼都不用改
  • 測試時可以傳入 Mock 實作，隔離外部依賴

這就是「面向介面程式設計（programming to an interface）」的實踐。

A5

Spring 啟動時會丟出 NoUniqueBeanDefinitionException——它找到兩個候選但不知道選哪個。

兩種解法：

  • @Primary：標在其中一個實作上，讓它成為預設首選——適合「大多數情況用這個」的場景
  • @Qualifier("beanName")：在注入點點名指定——適合「不同注入點需要不同實作」的場景，精確控制

A6

預設是 Singleton：整個 Application 共用同一個實例，節省記憶體、適合無狀態的 Service。

加上 @Scope("prototype") 後，每次注入或呼叫 getBean() 都建立全新物件。

  • Singleton 適合：OrderService、UserService 等無狀態業務邏輯類別
  • Prototype 適合：每次請求需要獨立狀態的物件，例如包含 mutable 狀態的 command/builder 物件

A7

在標了 @Configuration 的類別裡，寫一個標了 @Bean 的方法，方法回傳值就是要登記的物件： 

@Configuration
public class AppConfig {
    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper();
    }
}

Spring 啟動時會執行這個方法，把回傳的 ObjectMapper 收進 IoC 容器。其他 Bean 就可以透過建構子注入正常使用它，和 @Component Bean 完全一樣。
