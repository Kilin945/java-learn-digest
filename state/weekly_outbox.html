📘 每週回顧 · Java / Spring Boot · 2026-08-14
這週你學了 DTO / Entity 分離 與 Bean Validation，來把它們串起來想一遍吧

這週我們從「為什麼不能把 Entity 直接回傳給前端」出發，一路學到用 DTO 把關輸出入欄位，再加上 Bean Validation 做資料驗證。以下 8 題，混合這週的主題，幫你做主動回想（active recall）。建議先自己想過一輪答案，再往下對答案。

  1. （基礎） Controller 如果直接把 User entity 回傳給前端，實際上會發生什麼事？為什麼這樣做很危險？
  2. （基礎） DTO 和 Entity 是什麼關係？DTO 可以說是「對應資料庫表格的類別」嗎？
  3. （應用） 要把 User entity 轉成只含 id、name、email 的 UserDto，通常怎麼寫這個轉換？
  4. （應用） 前端呼叫「更新使用者」API 時，如果 Controller 參數直接用 User entity 接收，可能會被動什麼手腳？要怎麼設計 Request DTO 來避免？
  5. （應用） 只在 DTO 欄位上寫 @NotNull 就會生效嗎？Controller 端還要加上什麼，Spring 才會真的觸發檢查、擋下不合法資料？
  6. （混合思考） 如果 Request DTO 的 name 欄位傳進來的是空字串 "" 或純空白字串 " "，@NotNull 擋得住嗎？該換成哪個 annotation？
  7. （混合思考） 承上題，如果還想限制 name 長度要在 2～20 字之間，並且驗證失敗時要回傳自訂錯誤訊息，要加上哪個 annotation、怎麼寫？它可以跟 @NotBlank 一起疊加使用嗎？
  8. （綜合） 現在要設計一個「使用者註冊」用的 Request DTO：前端只能填 name、email，不能填 id、role；name 不可空白，長度限制 2～20 字。這個 DTO 會用到這週學的哪些技巧？請整合說明。
—— 解答 ——
  1. Entity 對應資料庫表格，包含所有欄位（甚至 password、身分證號等機密資料）。直接回傳 entity，Spring 會把「全部欄位」一起序列化成 JSON 送出去，等於把機密資料也一起洩漏給前端。
  2. DTO（Data Transfer Object）是自己寫的普通類別，只放要給前端看的欄位，跟資料庫表格沒有直接關係。它的角色是在 Entity 和前端之間做「欄位把關」，不是資料庫的對應物。
  3. 在 DTO 裡寫一個吃 Entity 的建構子（constructor），把要留下的欄位（id、name、email）一個一個複製過去；password 等機密欄位不寫進建構子，自然就不會出現在轉出來的 DTO、也不會被序列化送出。
  4. 如果直接用 entity 接收，前端可以硬塞 id、role 等不該由使用者決定的欄位，造成資料被竄改（例如把自己 role 改成 admin）。解法是另外寫一個 Request DTO，裡面只放允許填寫的欄位（如 name、email），沒宣告的欄位就算前端塞了也不會被綁定進來。
  5. 不夠。欄位上的 @NotNull 只是「宣告規則」，要在 Controller 方法的參數前加上 @Valid，Spring 才會真正觸發驗證；不合法的資料會被擋下並自動回傳 400 Bad Request。
  6. 擋不住。@NotNull 只檢查欄位是不是 null，空字串或純空白字串仍會通過。字串型別要用更嚴格的 @NotBlank，才能真正擋下空值 / 空字串 / 純空白字串。
  7. 用 @Size(min = 2, max = 20, message = "name 長度需介於 2 到 20 字")。可以，@Size 跟 @NotBlank 可以疊加在同一個欄位上一起使用，各自負責不同的驗證面向。
  8. 會用到：① 寫一個獨立的 Request DTO（只放 name、email 兩個欄位，不含 id、role，避免竄改）；② 在 name 欄位疊加 @NotBlank（擋空值/空字串/純空白）與 @Size(min=2, max=20)（限制長度並自訂錯誤訊息）；③ Controller 方法參數加上 @Valid，讓 Spring 真正觸發這些驗證，不合法就回 400。
