本週走過的路

String 不可變與 StringBuilder → 建構子注入 vs 欄位注入 → Bean 生命週期與 scope → AOP 的起點。先自己想一遍答案，再往下看解答。

🧠 回想題

Q1. 在 for 迴圈裡用 s = s + x 組一份電文字串，為什麼會產生大量垃圾？改用 StringBuilder 後，什麼時候才呼叫 toString()？

Q2. StringBuffer 和 StringBuilder 的差別是什麼？一個方法內的區域變數組字串，該選哪個？為什麼？

Q3. String 設計成 immutable，至少說出三個好處（提示：HashMap key、執行緒、字串池）。

Q4. 欄位注入（@Autowired private）在寫單元測試時會遇到什麼麻煩？建構子注入怎麼解決？

Q5. 建構子注入可以把依賴宣告成 final，這帶來什麼保證？如果兩個 Bean 循環依賴，建構子注入會發生什麼事？你覺得這是好事還是壞事？正確的解法是什麼？

Q6. 請依序寫出 Bean 的生命週期四個階段（含 @PostConstruct、@PreDestroy 各在什麼時間點）。為什麼 ErrorCodeService 的啟動自檢只跑一次？

Q7. singleton、prototype、request 三種 scope 各是什麼意思？如果 singleton Bean 裡注入了一個 prototype Bean，每次呼叫會拿到新物件嗎？要怎麼修？

Q8.（綜合）假設有個 singleton 的 Service，欄位注入一個 prototype 的 Bean，裡面存了「目前請求的使用者 ID」。請指出這段設計有哪兩個問題，並說明 AOP 想解決的是哪一類重複（以今天學的交易、log、權限檢查為例）。

—— 解答 ——

A1. String 內容不可變，每次相加都新造一個物件並複製整串舊內容，迴圈跑 N 次就產生 N 個中間物件，變成垃圾等 GC。編譯器只優化「單行」的相加，迴圈內不會幫你優化。改用 StringBuilder 在迴圈中 append，最後只呼叫一次 toString()。

A2. 兩者只差 synchronized 這把鎖：StringBuffer 有鎖（執行緒安全但慢），StringBuilder 沒鎖（快）。區域變數只有自己的執行緒看得到，不需要鎖，所以選 StringBuilder。

A3. ① 安全：內容不會被偷改（例如當作參數或設定值傳遞）。② 可當 HashMap key：內容不變，hashCode 可以快取，不會放進去後 hash 值變了就找不到。③ 天生 thread-safe：不可變就不用同步。④ 字串池（String Pool）因為不可變才能放心共用同一個物件。

A4. 欄位注入把依賴藏在 private 欄位，外面看不出類別需要什麼；測試時 new 出來欄位是 null，得靠 Spring 容器或反射才塞得進去。建構子注入把依賴寫在簽章上，缺什麼一眼看到，測試直接 new Service(mockA, mockB) 即可。

A5. final 保證物件建好後依賴就定死、不可能是 null、也不會被中途換掉。循環依賴時，建構子注入讓 Spring 啟動當場失敗——這是好事，問題在上線前就爆出來，而不是跑到一半才出事。正確解法是拆職責、抽出第三個 Bean，而不是改成欄位注入或用 @Lazy 繞過去。

A6. ① 建構（new 出物件）→ ② 注入（依賴塞進來）→ ③ @PostConstruct（依賴到齊後的初始化，在使用前跑）→ ④ 使用 → ⑤ @PreDestroy（容器關閉前的清理）。ErrorCodeService 是 singleton，整個容器只有一個物件，生命週期只走一遍，所以啟動自檢只跑一次。

A7. singleton（預設）：整個容器一份；prototype：每次跟容器要都給新的；request：每個 HTTP 請求一份。singleton 裡注入 prototype，只會在建 singleton 的那一次注入，之後永遠是同一個，不會每次新的。修法：用 ObjectProvider（或 lookup method）在需要時現拿。

A8. 問題一：prototype 只注入一次，所以名義上是「每次新的」，實際上被 singleton 綁死成同一份。問題二：singleton 全容器共用，不能放請求專屬狀態（使用者 ID），多個請求同時進來會互相覆蓋。請求專屬資料應放 request scope 或當參數傳遞。
AOP 解決的是「橫切邏輯」的重複：沒有 AOP 時，每個業務方法都要手寫權限檢查、log、開交易與 commit/rollback，容易漏寫、難統一修改、還淹沒業務邏輯。AOP 把它們抽成一份統一套用，@Transactional、@Secured 就是這樣取代手寫行。
