這週目前只有一課：IoC 與依賴注入：為什麼不要自己 new，外加一題手寫排序練習（Integer[] 含 null）。下面 6 題由淺入深，先自己想，再看信末解答。

小提醒：先在腦中或紙上寫出答案，再往下拉，主動回想效果最好。

Q1. 在 Spring 裡，IoC（Inversion of Control，控制反轉）反轉的是什麼？誰把控制權拿走了？

Q2. 在 OrderService 裡直接寫 new PaymentGateway()，會帶來哪兩個主要問題？（提示：測試、替換實作）

Q3. Dependency Injection（DI，依賴注入）常見有三種方式：constructor、setter、field。Spring 官方比較推薦哪一種？為什麼？

Q4. 手寫排序 Integer[]（可能含 null）時，動手前第一件事應該先問什麼？為什麼這個問題不能跳過？

Q5. 承 Q4，若要「null 放最後」，整體做法分成哪三步？為什麼只對前 n 個元素做插入排序，就不會 NPE？

Q6. 承 Q5，若改成「null 放最前面」，要怎麼調整？另外請回想：這題跟 IoC／DI 的共同精神是什麼？（開放式，說出你的想法即可）

—— 解答 ——

A1. 反轉的是「物件的建立與依賴組裝」的控制權。原本由我們的程式碼自己 new，現在交給 Spring 容器（IoC container）負責建立、組裝、管理生命週期。

A2. (1) 緊耦合（tight coupling）：OrderService 綁死具體類別，想換成別的實作就得改原始碼。(2) 難以測試：沒辦法輕易塞 mock／stub，單元測試會連到真的外部服務。

A3. 推薦 constructor injection。依賴可以宣告成 final（不可變）、物件建好就是完整狀態、缺依賴時啟動即失敗，測試時也能直接用 new 傳入 mock，不需要 Spring。

A4. 先問「null 要放前面還是後面？」。這是規格（需求）問題，不同答案會讓實作方向不同；沒先問清楚就寫，容易做出不符需求的版本。

A5. 三步：(1) 分離：把非 null 元素依序搬到陣列前面，n 就是非 null 個數；(2) 只對前 n 個做插入排序；(3) 把 n 之後的位置補回 null。因為前 n 個全是非 null，比較時的拆箱（unboxing，Integer 轉 int）不會遇到 null，所以不會 NPE。

A6. 改成從尾端往前填：非 null 元素從陣列尾端往前放，前面剩下的位置補 null，再只對後 n 個做插入排序。
共同精神（參考答案）：把「變動、危險的部分」隔離開。IoC 把「怎麼建立物件」交給容器；排序題把 null 先隔離出去，核心邏輯只面對乾淨的資料。職責清楚、核心邏輯單純，就更好測、更穩。
