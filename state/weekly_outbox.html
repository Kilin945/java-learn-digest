📘 每週回顧 · Java / Spring Boot · 2026-09-11

🧠 主動回想：這週學了什麼？

別急著往下滑看解答，先自己想想看每一題怎麼回答，這樣記得才牢。

  1. Self-invocation：如果一個 Service 裡的 methodA() 內部直接用 this.methodB() 呼叫另一個標了 @Transactional 的方法 methodB()，這個交易會生效嗎？為什麼？
  2. Rollback 預設行為：@Transactional 的方法丟出 IOException（一個 checked exception）時，預設會不會 rollback？要怎麼讓它會 rollback？
  3. 吞掉例外：如果方法內用 try-catch 抓到例外只寫了 log.error(...)，沒有 rethrow，@Transactional 會不會 rollback？為什麼 Spring「不知道出事」？
  4. 交易邊界設計：一個 @Transactional 的方法裡，先更新 DB、再呼叫外部 API 寄一封 Email 通知，這樣設計有什麼問題？你會怎麼改？
  5. 測試分類：單元測試（unit test）和整合測試（@SpringBootTest）最核心的差異是什麼？各自的優缺點？
  6. contextLoads()：一個內容完全空白的 contextLoads() 測試方法，加上 @SpringBootTest 之後在測什麼？為什麼方法內什麼都不寫也有意義？
  7. 綜合題：如果你要測試「交易 rollback 邏輯有沒有正確設定 rollbackFor」，你覺得該用單元測試還是整合測試？為什麼？

—— 解答 ——

  1. Self-invocation：不會生效。Spring 的 @Transactional 是靠代理人（proxy）機制實作的，只有「從代理人外部」呼叫方法時才會經過代理人、觸發交易邏輯。用 this.xxx() 是繞過代理人的內部呼叫（self-invocation），所以交易不會啟動，也不會 rollback。
  2. Rollback 預設行為：不會。@Transactional 預設只在遇到 unchecked exception（RuntimeException / Error）時才 rollback。要讓 checked exception（如 IOException）也觸發 rollback，必須明確指定 @Transactional(rollbackFor = IOException.class)。
  3. 吞掉例外：不會 rollback。@Transactional 只有在例外「真的往外拋出方法邊界」時才會發現。try-catch 抓住例外又不 rethrow，等於把錯誤訊息藏起來，Spring 從頭到尾沒看到任何例外，交易照樣正常 commit——即使資料其實已經壞掉。
  4. 交易邊界設計：問題是外部 API／寄信這類慢操作會佔用資料庫連線，讓交易被拉長，進而拖住連線池（connection pool），塞住其他無關請求。改法：把 DB 操作留在交易內，交易結束（commit 後）再另外呼叫外部 API/寄信，例如拆成兩個方法或用事件（event）非同步觸發。
  5. 測試分類：單元測試只測一個方法或 class 本身的邏輯，不碰資料庫、網路，跑得快；整合測試用 @SpringBootTest 真的啟動整個 Spring 應用程式、把所有 bean 兜起來運作，能抓到「元件裝不起來」的問題，但速度慢很多。
  6. contextLoads()：它在測「整個 Spring 應用程式的所有 bean 能不能成功組裝並啟動」。方法體是空的沒關係，因為重點根本不是方法裡的程式碼邏輯，而是 @SpringBootTest 這個 annotation 觸發的 Spring context 啟動過程——只要啟動失敗（例如某個 bean 缺依賴），這個測試就會噴錯。
  7. 綜合題：用整合測試（@SpringBootTest）比較合適。因為要驗證 rollback 是否真的發生，需要一個真正跑起來的 transaction manager 和資料庫（或內嵌資料庫）互動，這已經超出「單一方法邏輯」的範圍，屬於「元件兜在一起是否正確運作」的整合層級問題。
