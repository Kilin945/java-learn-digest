✅ 參考解答
A1．第三方類別無法加 @Component
@Component 需要能修改原始碼才能加上去。若使用的是外部 JAR（例如 Jackson 的 ObjectMapper、資料庫驅動的 DataSource），原始碼不在你手上，就無法直接標註。
此時在 @Configuration 類別裡寫一個 @Bean 方法，手動 new 出該物件並回傳，Spring 容器就會接管它的生命週期。
A2．@Bean 方法以參數接收依賴
將依賴的 Bean 型別宣告為 @Bean 方法的參數，Spring 在呼叫該方法前會先解析並注入對應的 Bean： 
@Bean
public JdbcTemplate jdbcTemplate(DataSource dataSource) {
    return new JdbcTemplate(dataSource);
    // Spring 自動找到 DataSource Bean 傳進來
}
A3．同型別多 Bean 的解法
不處理的話，Spring 注入時拋 NoUniqueBeanDefinitionException。常見兩種解法：
1. @Primary：在「預設首選」那顆 Bean 上標記，適合有明顯主要選項的場景（全域預設）。
2. @Qualifier("名稱")：在注入點指定 Bean 名稱，適合需要精確控制、場景各異的情況（每個注入點自行決定）。
A4．@Qualifier 優先級高於 @Primary
最終注入的是 PGDataSource。
@Qualifier 是「點名指定」，優先級高於 @Primary 的全域預設。@Primary 只在注入點沒有任何限定詞時才生效，只要注入點出現 @Qualifier，Spring 就直接依名稱比對，@Primary 的設定被忽略。
A5．Singleton vs. Prototype 對比
Singleton（預設） Prototype
建立時機 容器啟動時（Eager） 每次 getBean / 注入時
實例數量 整個容器唯一一個 每次得到全新物件
狀態共享 全域共用，注意執行緒安全 各自獨立，互不影響
典型場景 Connection Pool、Service Email Builder、Request-scoped 物件
A6．@PostConstruct 與 @PreDestroy 的時機
@PostConstruct：Bean 被 Spring 實例化、所有依賴注入完畢之後立刻呼叫。典型用途：預熱 Cache、建立資料庫 Schema、載入設定檔。

@PreDestroy：ApplicationContext 關閉、Spring 準備銷毀 Bean 之前呼叫。典型用途：關閉 DB 連線、釋放執行緒池、刷寫未提交的 Buffer。
A7．Prototype 不觸發 @PreDestroy 的原因與解法
Spring 容器對 Prototype Bean 不保留參考——把物件交出去後就不再追蹤，因此容器關閉時根本不知道還有哪些 Prototype 實例存活，自然無法觸發 @PreDestroy。

解法：由取得 Prototype Bean 的呼叫端自行負責清理。若該 Bean 實作了 DisposableBean 介面（或有 destroy() 方法），呼叫端在使用完畢後手動呼叫 destroy()；或將 Bean 包在 try-with-resources 裡（實作 AutoCloseable）確保資源被釋放。
