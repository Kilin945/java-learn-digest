📘 每週回顧 · Java / Spring Boot · 2026-08-21

這週我們從 Bean Validation 收尾，一路把「統一例外處理」蓋成一棟完整的房子，最後又開了一扇新窗——Spring Data JPA。來做幾題主動回想，把這些串起來 💪

  1. Q1（Bean Validation 收尾）： 當 @Valid 標註的欄位驗證失敗時，Spring 預設會丟出哪種例外？我們用什麼註解組合把它攔下來、整理成「欄位對應錯誤原因」的乾淨 JSON？
  2. Q2（動機回想）： 在還沒有 @RestControllerAdvice 之前，每個 Controller 各自 try-catch 處理 ResourceNotFoundException 會遇到什麼具體痛點？這個痛點怎麼促成了「統一例外處理」這個主題？
  3. Q3（角色分工）： @RestControllerAdvice 和 @ExceptionHandler 各自負責什麼？請用一句話說明兩者如何合作，把分散在各 Controller 的例外處理集中到一個 GlobalExceptionHandler。
  4. Q4（進化過程）： 我們把最早回傳純文字 String 的例外處理範例，升級成回傳 ResponseEntity<ErrorResponse>。這個升級解決了什麼問題？為什麼順便設定正確的 HTTP 狀態碼（例如 404）很重要？
  5. Q5（萬用備援）： 為什麼要在 GlobalExceptionHandler 裡額外加一個 @ExceptionHandler(Exception.class)？它回傳的狀態碼通常是多少？如果沒有它，使用者會看到什麼？
  6. Q6（整合＋原則）： 假設同一個 GlobalExceptionHandler 裡同時有 ResourceNotFoundException 專屬的 handler 和 Exception.class 萬用 handler，當丟出 ResourceNotFoundException 時，Spring 會選哪一個？依據的是什麼原則？
  7. Q7（新主題）： 什麼是 ORM？在 Spring Data JPA 裡，Repository 介面只要繼承 JpaRepository，就能得到哪些 CRUD 方法而不用自己寫實作？
  8. Q8（跨主題整合，進階）： 如果在一個繼承 JpaRepository 的 Repository 中用 findById(id) 查不到資料，你會怎麼設計程式碼，讓它丟出 ResourceNotFoundException，並讓這週學到的 GlobalExceptionHandler 正確接手、回傳結構化的 404 JSON？

—— 解答 ——

A1： 會丟出 MethodArgumentNotValidException。用 @RestControllerAdvice 搭配 @ExceptionHandler(MethodArgumentNotValidException.class) 攔截它，再從例外物件裡取出每個欄位的錯誤訊息，組成乾淨的 JSON 回應。

A2： 痛點是程式碼重複又分散——每個 Controller 方法都要自己寫一次 try-catch，難以維護、容易漏掉、風格也不一致。這個痛點正是引入 @RestControllerAdvice（全域例外處理中心）的動機：把邏輯集中到一個地方。

A3： @RestControllerAdvice 標註「這是一個全域例外處理中心」的 class；@ExceptionHandler 標註在 class 裡的方法上，指定「這個方法要處理哪一種例外」。兩者合作，就能把原本散落各 Controller 的處理邏輯，集中變成一個 GlobalExceptionHandler。

A4： 純文字 String 對前端來說不好解析、資訊也不夠結構化；升級成 ResponseEntity<ErrorResponse> 後，回應變成一致的 JSON 結構（例如包含 message、status 等欄位），前端可以穩定地解析。正確設定狀態碼（如 404）則讓 HTTP 語意正確，前端也能依狀態碼做不同處理，而不是永遠拿到 200。

A5： 因為程式一定還有沒被特別預期、沒被個別 handler 涵蓋到的例外（例如 NullPointerException），如果沒有萬用備援，使用者會直接看到伺服器原始的錯誤堆疊（stack trace），既不專業也可能洩漏系統細節。加上 @ExceptionHandler(Exception.class) 後，這些例外會被統一包成 ErrorResponse，回傳 500 Internal Server Error。

A6： Spring 會選 ResourceNotFoundException 專屬的 handler。依據的原則是「最精確符合」（most specific match）——Spring 會優先挑選跟實際丟出的例外型別最接近、最具體的 @ExceptionHandler，只有在找不到更精確的對應時，才會落到 Exception.class 這個萬用備援。

A7： ORM（Object-Relational Mapping）是把資料庫的資料表對應成程式裡的物件，讓開發者用物件操作取代直接寫 SQL。在 Spring Data JPA 中，Repository 介面只要 extends JpaRepository，就會自動獲得 save()、findById()、findAll()、deleteById() 等基本 CRUD 方法，完全不用自己寫實作。

A8： 可以在 Service 層呼叫 repository.findById(id)，它回傳的是 Optional<T>；用 .orElseThrow(() -> new ResourceNotFoundException(...)) 在查不到資料時主動丟出例外。因為這個例外型別已經在這週建好的 GlobalExceptionHandler 裡有對應的 @ExceptionHandler，Spring 會自動接手，回傳結構化的 ErrorResponse JSON 並設定 404 狀態碼——這正是這週兩個主題串起來的地方。
