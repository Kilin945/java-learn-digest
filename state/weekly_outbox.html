Q3　（基礎）

Spring Security 在請求流程中放在哪裡？它是什麼結構？用哪個 bean 來設定「哪些路徑放行、哪些要登入」？

Q4　（應用）

下面這行 log 有什麼問題？你會怎麼改？

Q5　（應用）

為什麼密碼不能原文存進資料庫？請說明 PasswordEncoder 的 encode() 與 matches() 各在什麼時機用，以及 BCrypt 的 salt 帶來什麼好處。

Q6　（應用）

Spring Security 不知道你的使用者存在哪裡。你要實作哪個 interface 的哪個方法？該方法回傳什麼？找不到使用者時要做什麼？之後誰負責比對密碼？

Q7　（綜合）

看這段設定：
.authorizeHttpRequests(a -> a
  .anyRequest().authenticated()
  .requestMatchers("/admin/**").hasRole("ADMIN"))
這樣寫會出什麼問題？正確順序該怎麼排？

Q8　（綜合）

情境：使用者 Amy 帶著正確帳密登入成功，角色只有 USER，去呼叫 /admin/users（規定要 ADMIN）。(a) 會回幾號狀態碼？為什麼？(b) 若她沒登入就直接打這支 API 呢？(c) 這時伺服器要記一筆 log 追蹤這次存取，你會記哪些欄位、避免記哪些？

—— 解答 ——

A1　Authentication（認證）＝「你是誰」，失敗回 401；Authorization（授權）＝「你能做什麼」，失敗回 403。永遠先認證、再授權。

A2　設定 logging.structured.format.console，可選 ecs、logstash、gelf。MDC 的 requestId 會自動成為 JSON 的一個欄位，日誌平台就能依欄位搜尋。

A3　它是放在 Controller 前面的 Filter Chain（過濾器鏈），每個請求都要先通過；認證與授權都在鏈上完成。用 SecurityFilterChain bean 設定，permitAll 放行、authenticated 需登入。

A4　直接印整個物件，會呼叫 toString()，把 password、token 一起寫進 log，造成敏感資料外洩。改法：只記 userId 這類內部編號，例如 log.info("user login: userId={}", user.getId())；真的必須記就先遮罩；也可以讓 toString() 排除敏感欄位。

A5　原文存放一旦資料庫外洩，所有密碼立刻曝光。存檔（註冊／改密碼）時用 encode() 轉成帶 salt 的不可逆雜湊；登入時用 matches(輸入密碼, 資料庫雜湊) 比對。salt 是隨機加進去的值，讓相同密碼產生不同雜湊，無法用彩虹表（rainbow table，預先算好的雜湊對照表）一次破解。

A6　實作 UserDetailsService 的 loadUserByUsername(帳號)，回傳含密碼雜湊的 UserDetails；找不到就丟 UsernameNotFoundException。之後由 Spring 用 PasswordEncoder.matches() 比對密碼，你不用自己比。

A7　規則是由上往下比對，第一個符合就採用。anyRequest() 會吃掉所有請求，後面的 /admin/** 規則永遠不會生效（新版 Spring Security 甚至會在啟動時直接報錯）。正確：先寫具體的 requestMatchers("/admin/**").hasRole("ADMIN")，anyRequest().authenticated() 放最後。

A8　(a) 403：Amy 已通過認證（知道她是誰），但角色 USER 不夠，屬於授權失敗。(b) 沒登入＝認證失敗，回 401（先認證再授權，根本還沒走到角色判斷）。(c) 記 requestId（MDC 自動帶）、userId、路徑、HTTP 方法、結果狀態碼；不要記密碼、token、卡號，也別直接印整個 user 物件。
