📘 每週回顧 · Java / Spring Boot · 2026-10-16
這週我們把 Spring Security 從頭走了一遍：取得登入者 → 方法層級授權 → REST API 的 CSRF／STATELESS → 整個請求流程。先別翻到最後，每題試著自己回想一下，再對解答。
🧠 回想題

Q1. 認證成功後，登入者的資訊存放在哪裡？Controller 有哪兩種方式可以直接拿到目前使用者？

Q2. 如果使用者的角色是 ADMIN，從 Authentication 的 authorities 看到的字串會是什麼？為什麼？

Q3. 要讓 @PreAuthorize 生效，需要先在設定類別上加什麼 annotation？

Q4. 請各寫出一個 @PreAuthorize 的 SpEL 範例：(a) 只有 ADMIN 能呼叫；(b) 只有「本人」能呼叫（參數名為 username）。檢查不符時回什麼狀態碼？

Q5. 一個純 REST API，帳密完全正確，但 POST／PUT／DELETE 一直回 403，GET 卻正常。最可能的原因是什麼？該怎麼改？

Q6. SessionCreationPolicy.STATELESS 代表什麼？它對「每個請求」帶來什麼要求？

Q7. 請把一個請求的處理順序依序說出來（從 Filter Chain 到 Controller），並指出 401 與 403 各發生在哪一關。

Q8. 一份完整的 SecurityConfig（REST API 版）會串起哪幾個設定？為什麼下一步要學 JWT？

—— 解答 ——

A1. 放在 SecurityContext。Controller 可用 @AuthenticationPrincipal UserDetails，或直接宣告 Authentication 參數來取得。

A2. 會是 ROLE_ADMIN。角色會自動帶 ROLE_ 前綴；用 hasRole('ADMIN') 時 Spring 會幫你補上前綴再比對。

A3. @EnableMethodSecurity。

A4. (a) @PreAuthorize("hasRole('ADMIN')")；(b) @PreAuthorize("#username == authentication.name")。不符時在方法執行前就擋下，回 403。

A5. Spring Security 預設開啟 CSRF 保護，會擋掉會改資料的請求（POST／PUT／DELETE），GET 不受影響。解法：在 SecurityFilterChain 把 csrf 關閉，並設 STATELESS。

A6. 代表不建立、也不依賴 session／cookie 來認人。因此每個請求都要自己證明身分（例如帶帳密或 token）。

A7. 請求先進 Filter Chain → 認證（失敗回 401）→ 授權（失敗回 403）→ 才進 Controller。401 是「你是誰我不確定」，403 是「我知道你是誰，但你沒權限」。

A8. 串起：csrf 關閉、STATELESS、路徑規則（哪些路徑要什麼角色）、httpBasic、BCrypt（密碼雜湊）。因為 STATELESS 下每個請求都要自證身分，httpBasic 每次都送帳密不理想，所以下一步學 JWT（用簽章 token 代表身分）。
