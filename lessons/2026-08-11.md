## DTO 與 entity 為什麼要分開 · 第 4 步

### 概念：Request DTO（輸入方向的防護）

前幾步教的是「送資料出去」的方向：Entity → DTO，藏起機密欄位。這一步教「收資料進來」的方向：前端傳資料進來時，Controller 也不該直接用 entity 接收前端傳來的 JSON，否則 Spring 的欄位綁定（binding）機制會把 JSON 裡任何跟 entity 欄位同名的值都填進去——包含前端不該碰的 id、role 等欄位，造成竄改風險。

解法是另寫一個「輸入用」的 DTO（例如 `CreateUserRequest`），只放允許前端填寫的欄位。前端就算多塞欄位，因為 DTO 類別上沒有對應欄位，那些值會被直接忽略。

### 程式碼

```java
// Request DTO：只放允許前端填寫的欄位
public class CreateUserRequest {
    private String name;
    private String email;
    // getter / setter 略
}

@PostMapping("/users")
public UserDto createUser(@RequestBody CreateUserRequest req) {
    User user = new User();
    user.setName(req.getName());
    user.setEmail(req.getEmail());
    user.setRole("USER"); // 權限由後端自己決定
    userRepository.save(user);
    return new UserDto(user);
}
```

### 術語表

| 術語 | 中文 | 定義 |
|---|---|---|
| Request DTO | 請求用的傳輸物件 | 專門接收前端傳入資料的 DTO，只放允許填寫的欄位 |
| @RequestBody | 請求主體標註 | 告訴 Spring 把 JSON 自動轉成指定物件 |
| binding | 欄位綁定 | JSON 的 key/value 自動填進物件同名欄位的過程 |
| tamper | 竄改 | 使用者惡意修改不該由他更改的資料 |

### 主題小結

到這一步，「DTO 與 entity 為什麼要分開」的核心概念已涵蓋：為什麼不能直接回傳 entity（機密外洩）、DTO 是什麼、entity→DTO 的轉換（輸出防護）、以及 DTO→entity 方向的 Request DTO（輸入防護）。這個主題告一段落。
