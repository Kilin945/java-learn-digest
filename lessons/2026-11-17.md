## A2 第 2 篇 · 建構子注入的 final;循環依賴時啟動就失敗為什麼是好事

**題目**:@Autowired 欄位注入為什麼 IDE 給黃線?建構子注入好在哪?

### 題目在問什麼
- final:欄位只能在建構子賦值一次,之後不能換。
- 循環依賴:A 需要 B、B 又需要 A,誰都沒辦法先建好。
- 要答到:① final 保證什麼 ② 循環依賴時兩種注入各自怎樣 ③ 為什麼啟動就失敗是好事。

```java
// 輸入:兩個互相需要對方的類別(典型寫法,簡化)
class A { A(B b) {} }
class B { B(A a) {} }
// 輸出(建構子注入):啟動當場失敗
// 輸出(欄位注入):可能啟動成功,問題被藏起來
```

### 解題思路
1. 題目問「好在哪」,先確認建構子注入多了什麼能力:可以寫 final(本篇)。
2. final 欄位只能在建構子賦值,依賴定死(本篇)。
3. 建構子要的東西必須先備齊才能 new,循環依賴時兩邊卡住(本篇)。
4. 卡住發生在容器建 Bean 階段,所以啟動就爆(本篇)。
5. 可測試性、依賴藏起來:第 1 篇已講。

### 答案
建構子注入可把依賴宣告成 final,建好就不會被換;循環依賴時 Spring 啟動當場失敗,問題在上線前被逼出來,所以是好事。

```java
// 典型寫法(簡化)
@Service
public class OrderService {
    private final PaymentClient paymentClient; // 只能在建構子賦值一次

    public OrderService(PaymentClient paymentClient) { // 單一建構子,Spring 自動注入
        this.paymentClient = paymentClient;
    }

    void pay() {
        // this.paymentClient = other; // 編譯錯誤
        paymentClient.send();
    }
}
// 欄位注入不能加 final:物件建好後才由 Spring 反射塞入
```

### 第 1 輪 · 釐清:欄位標 final 到底保證了什麼?少了它又會怎樣?
final 鎖的是「指向」,不是物件內部資料。

```java
class OrderService {
    private final PaymentClient client;
    private PaymentClient client2;
    OrderService(PaymentClient c) { this.client = c; }
    void bug() {
        // client = null;   // 編譯擋下
        client2 = null;     // 編譯過,執行時才 NPE
        client.send();
    }
}
// ① 不會被手滑換掉或設成 null
// ② 不賦值編譯不過 → 不會有依賴是 null 的物件
```

### 第 2 輪 · 追原因:為什麼循環依賴時建構子注入啟動就失敗,欄位注入卻可能跑得起來?

```java
// 建構子注入(簡化示意)
// new A 需要 B → new B 需要 A → A 還沒建好 → 死結
// 啟動階段丟 BeanCurrentlyInCreationException

// 欄位注入(簡化示意)
// new A() 空殼;new B() 空殼;事後反射互相塞
// 先蓋空殼、再補依賴,繞過死結

// Spring Boot 2.6 起預設禁止欄位注入的循環依賴
// (spring.main.allow-circular-references=false),設 true 又能跑,問題只是被蓋住
```

### 第 3 輪 · 反事實:如果循環依賴被欄位注入悄悄放過,會壞在哪?

```java
class A { @Autowired B b; void run() { b.run(); } }
class B { @Autowired A a; void run() { a.run(); } }
// 啟動沒事;上線後某條路徑呼叫 a.run()
// a.run → b.run → a.run → ... StackOverflowError(執行期才爆)
// 建構子注入:啟動就報錯,上不了線
```

### 追問:循環依賴時建構子注入會怎樣?遇到了該怎麼解?

```java
// 修之前
class A { A(B b) {} }
class B { B(A a) {} }
// 啟動失敗:循環依賴

// 修法:抽出共用邏輯
class Shared {}
class A { A(Shared s) {} }
class B { B(Shared s) {} }
// A → Shared ← B,單向無環

// 不要:改欄位注入或加 @Lazy 硬繞,環還在,只是延到執行期
```

### 為什麼要懂
新功能上線前一天,A 加了對 B 的依賴,B 早就依賴 A。懂的人看到啟動失敗會去拆職責;不懂的人可能把 @Autowired 欄位加回去讓它能跑,埋下定時炸彈。

### 結論
建構子注入讓依賴能宣告成 final,也讓循環依賴在啟動時就爆出來。遇到環,拆職責、抽第三個 Bean,不要用欄位注入或 @Lazy 繞過。

### 術語表
| 術語 | 白話定義 |
|---|---|
| final | 欄位只能賦值一次,不能指到別的物件 |
| 循環依賴 | A 需要 B、B 又需要 A,誰都建不出來 |
| Bean | 由 Spring 容器建立與管理的物件 |
| BeanCurrentlyInCreationException | Spring 建 Bean 時發現環而丟出的例外 |
| StackOverflowError | 方法無出口互相呼叫,呼叫堆疊塞滿 |
| @Lazy | 讓 Spring 延後建立依賴,繞過啟動錯誤但環還在 |
