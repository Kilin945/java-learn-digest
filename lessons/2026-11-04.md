## B9 第 3 篇 · 怎麼查：jstack 抓 thread dump，怎麼讀出卡在哪兩把鎖

**題目**：deadlock 是什麼？怎麼避免、怎麼查？

### 題目在問什麼
- thread dump：某一瞬間所有執行緒的快照（在做什麼、停在哪一行、握著或等著哪些鎖）。
- jstack：JDK 內附指令，對指定 PID 印出 thread dump。
- 要交出：怎麼抓，以及怎麼讀出「哪兩條執行緒、卡在哪兩把鎖」。
- 題目沒講：卡住不一定是死結，要會分辨死結和只是慢。

```bash
# 輸入：一個正在跑的 Java 程序（假設 PID 是 12345）
# 輸出：Thread-A 握著鎖 X 等鎖 Y；Thread-B 握著鎖 Y 等鎖 X
jps -l                    # 列出 Java 程序與 PID
jstack 12345 > dump.txt   # 拍快照
```

### 解題思路
1. 先確認是卡住不是慢（第 1、2 篇講症狀與避免）。
2. 用 jps 找 PID。（本篇）
3. jstack 隔幾秒拍兩三次。（本篇）
4. 拉到最底找 Found one Java-level deadlock。（本篇）
5. 對照兩條執行緒握著與等待的鎖位址。（本篇）
6. 照行號回到程式碼，看上鎖順序為什麼不一致。（本篇）

### 答案
用 jstack 抓 thread dump，有死結時 JVM 會在最底下印出「Found one Java-level deadlock」，列出哪兩條執行緒、各自等哪把鎖、那把鎖被誰握著。

```text
# 簡化示意
"Thread-A" #21 ...
   java.lang.Thread.State: BLOCKED (on object monitor)
        at Demo.methodA(Demo.java:12)
        - waiting to lock <0x...2340>
        - locked <0x...2350>

"Thread-B" #22 ...
   java.lang.Thread.State: BLOCKED (on object monitor)
        at Demo.methodB(Demo.java:25)
        - waiting to lock <0x...2350>
        - locked <0x...2340>

Found one Java-level deadlock:
=============================
"Thread-A":
  waiting to lock monitor 0x... (object 0x...2340),
  which is held by "Thread-B"
"Thread-B":
  waiting to lock monitor 0x... (object 0x...2350),
  which is held by "Thread-A"
```

### 第 1 輪 · 釐清：「waiting to lock <0x…>」和「locked <0x…>」後面那串是什麼？
那串是鎖物件在記憶體裡的位址，等於鎖的身分證。位址對得上，才知道兩條執行緒在搶同一把鎖。

```java
// 典型寫法（簡化）
Object lockX = new Object();   // 位址例如 0x...2340
Object lockY = new Object();   // 位址例如 0x...2350

synchronized (lockX) {         // 拿到 X → dump 印 locked <X>
    synchronized (lockY) {     // 拿不到 Y → dump 印 waiting to lock <Y>
    }
}
// A：握 2350 等 2340；B：握 2340 等 2350 → 圈閉起來。
// 只看到 BLOCKED 不算數，位址要互相對得上才是死結。
```

### 第 2 輪 · 挑戰假設：沒有「Found one Java-level deadlock」就一定不是死結嗎？
不一定，這一行只管 JVM 自己看得到的鎖。

```text
# 情況一：死結在資料庫。執行緒狀態是 RUNNABLE，停在 socketRead，沒有 Found 那行。
#         要去資料庫查鎖等待，不是靠 jstack。
# 情況二：ReentrantLock 等 java.util.concurrent 的鎖，加 -l 才會多印持有者：
jstack -l 12345 > dump.txt
# 情況三：只是慢。隔 5 秒再拍一次比對：
#         兩次都停在同一行同一狀態 → 真的卡住；位置有變 → 只是慢。
```

### 第 3 輪 · 連結經驗：OOM 調查抓 thread dump 和查死結，讀法差在哪？
抓法一樣，差別在帶著什麼問題去看。

```text
# OOM：看執行緒總數、是否大量堆在同一個方法
# 死結：看最底下 Found 那行、BLOCKED 的鎖位址對不對得上、兩條執行緒的行號
# 共通：先看狀態（RUNNABLE／BLOCKED／WAITING），再看 stack 最上面那行
```

### 追問：死結的四個必要條件是哪四個？只打破一個就夠嗎？
四個條件同時成立才會死結，所以打破任何一個就夠。實務上最好打破循環等待，也就是固定上鎖順序。

```text
1. 互斥：每把鎖同時只有一個 locked 持有者
2. 持有並等待：同一條執行緒同時有 locked 和 waiting to lock
3. 不可搶奪：synchronized 的鎖只能自己放
4. 循環等待：Found one Java-level deadlock 那段印出的圈

打破第 4 個最划算：
互斥是鎖的本意；一次拿齊所有鎖常做不到；硬搶會破壞資料；
所有人照同一順序拿鎖，圈就畫不出來。
```

### 為什麼要懂
正式環境突然不回應，重啟後又好了，卻沒留下證據。重啟前跑一次 jstack，就能指出哪兩行 code、哪兩把鎖互卡。

### 結論
查死結：jps 找 PID → jstack 拍快照 → 看最底下的 Found one Java-level deadlock → 用鎖位址對出互等的兩條執行緒。沒有這行時，要再排除資料庫鎖、j.u.c 鎖與單純變慢。

### 術語表
| 術語 | 白話定義 |
|---|---|
| thread dump | 某一瞬間所有執行緒的快照 |
| jstack | JDK 內附，對指定 PID 印出 thread dump 的指令 |
| jps | 列出本機 Java 程序與 PID |
| PID | 作業系統給程序的編號 |
| BLOCKED | 執行緒狀態，排隊等 synchronized 的鎖；單看不代表死結 |
| monitor | synchronized 背後那把鎖的正式名稱 |
