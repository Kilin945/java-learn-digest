## A1 第 2 篇 · 容器怎麼把依賴注入進來；測試時換成假物件

**題目：IoC / DI 是什麼？好處是什麼？**

### 題目在問什麼
- 依賴：A 類別要靠 B 類別才能工作，B 就是 A 的依賴。
- DI：A 不自己 new B，由別人（容器）從外面交給 A。
- 本篇要答：① 容器怎麼把依賴交進來；② 為什麼測試能換成假物件。

### 解題思路
1. IoC：建立與組裝交給容器（第 1 篇）。
2. **DI：容器看建構子型別，找對應 Bean 塞進去（本篇）。**
3. **好處：依賴從外面進來，測試可塞假物件（本篇）。**
4. 追問：欄位注入為什麼被警告（細節見 A2）。

### 答案
容器啟動時，看 Bean 建構子需要什麼型別，去容器找該型別的 Bean 傳進去，這就是 DI。依賴從外面傳進來，所以測試可以自己 new 並傳入假物件。

```java
// 典型寫法（簡化）
public interface CardRepository {
    int countAll();
}

@Service
public class CardService {
    private final CardRepository repo;

    // 建構子簽章 = 需求清單；只有一個建構子時 @Autowired 可省略（Spring 4.3 起）
    public CardService(CardRepository repo) {
        this.repo = repo;
    }

    public int count() { return repo.countAll(); }
}

// 容器啟動時（簡化示意）：
// ① 掃到 @Service CardService，讀建構子：要一個 CardRepository
// ② 在容器找型別是 CardRepository 的 Bean；沒建就先建
// ③ new CardService(那個 Bean)，存回容器
```

### 第 1 輪（釐清）：容器靠什麼判斷要塞哪個 Bean？
主要靠型別。對到一個就用；對到多個不會猜，要明確指定。

```java
public interface Notifier { void send(String msg); }

@Component
public class EmailNotifier implements Notifier { }

// 只有一個 Notifier：直接注入

@Component
public class SmsNotifier implements Notifier { }

// 兩個 Notifier：型別對到兩個，啟動時丟 NoUniqueBeanDefinitionException
// 解法一：@Primary 指定預設
// 解法二：@Qualifier 點名（Bean 預設名 = 類別名首字母小寫）
public AlertService(@Qualifier("emailNotifier") Notifier notifier) {
    this.notifier = notifier;
}
```

### 第 2 輪（反事實）：自己 new CardRepository，測試會壞在哪？
依賴被寫死，測試沒地方換掉它；有 DI，只要從外面傳不同物件。

```java
// 沒有 DI（簡化示意）
public class CardService {
    private final CardRepository repo = new RealCardRepository(); // 寫死
}
// 測 count() 一定連真 DB

// 有 DI：測試自己 new，不需要 Spring
class CardServiceTest {
    @Test
    void count_returnsWhatRepoSays() {
        CardRepository fake = () -> 3;
        CardService service = new CardService(fake);
        assertEquals(3, service.count());
    }
}

// 一定要啟動容器時：把 Bean 換成 Mockito 假物件
// Spring Boot 3.4 以上 @MockitoBean；舊版 @MockBean
// @MockitoBean CardRepository repo;
```

### 第 3 輪（連結經驗）：@Autowired 與建構子注入，容器實際做了什麼？
anki-forge 的 configurable service bean 同一機制：Service 只宣告要什麼型別，實際實作由容器決定。

```java
// 典型寫法（簡化），不是專案原始碼

// 欄位注入
@Service
public class CardService {
    @Autowired
    private CardRepository repo;
}
// 容器：先 new CardService()（此時 repo 為 null），再用反射塞進 private 欄位

// 建構子注入
@Service
public class CardService {
    private final CardRepository repo;
    public CardService(CardRepository repo) { this.repo = repo; }
}
// 容器：new CardService(repo)，物件一出生依賴就齊
```

### 追問：欄位注入為什麼被 IDE 警告？

```java
// 欄位注入：依賴藏在欄位
class A { @Autowired private B b; }
// ① 從建構子看不出需要 B
// ② 測試 new A() 後 b 是 null，只能靠反射或啟動容器
// ③ 欄位不能 final

// 建構子注入：依賴寫在簽章
class A {
    private final B b;
    A(B b) { this.b = b; }
}
// new A(fakeB) 直接可測
// 完整版見 A2
```

### 為什麼要懂
想補單元測試卻得啟動整個 Spring、連真 DB 才跑得動，通常是依賴被寫死或用欄位注入。懂 DI 後，把依賴放建構子，測試可直接 new 並傳假物件，幾毫秒跑完。

### 結論
DI 就是容器依建構子需要的型別，把對應的 Bean 傳進來；依賴從外面進來，測試時就能換成假物件，業務碼不用動。

深入官方文件：[Dependency Injection（Spring Framework Reference）](https://docs.spring.io/spring-framework/reference/core/beans/dependencies/factory-collaborators.html)

### 術語表
| 術語 | 白話定義 |
|---|---|
| 依賴 | 一個類別要靠另一個類別才能工作，被靠的那個就是依賴 |
| 建構子注入 | 依賴寫在建構子參數上，由容器在建立物件時傳入 |
| 欄位注入 | 在欄位上加 @Autowired，容器建好物件後用反射塞值 |
| 反射 | 執行時動態讀寫類別內部成員，連 private 欄位也能寫 |
| 假物件（mock / fake） | 測試時取代真依賴的替身，回傳預設的值 |
| @Primary / @Qualifier | 同型別多個 Bean 時，前者指定預設，後者在注入點點名 |
| @MockitoBean | 把容器裡某個 Bean 換成 Mockito 假物件（舊版叫 @MockBean） |
