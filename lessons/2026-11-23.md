## A5 第 2 篇 · 其他失效情況：非 public、例外被自己吃掉、checked 例外預設不回滾；各自怎麼解

### ⭐ @Transactional 什麼時候會失效？

**題目在問什麼**

- 「失效」：方法上寫了 @Transactional，出錯時資料卻沒退回去（沒回滾），或根本沒開交易。
- 「回滾」：把這次交易內已寫進資料庫的修改全部撤銷。
- 第 1 篇講同類內部呼叫；本篇講非 public、例外被吃掉、checked 例外。
- 要答到：每種為什麼失效、怎麼看出來、怎麼解。

```java
// 情況 A：方法不是 public
@Transactional
private void saveA() { dao.insert(); }

// 情況 B：例外被自己 try-catch 吃掉
@Transactional
public void saveB() {
    try {
        dao.insert();
        dao.update();          // 假設丟 RuntimeException
    } catch (Exception e) {
        log.error(e);          // 沒有再往外丟
    }
}

// 情況 C：丟 checked 例外
@Transactional
public void saveC() throws IOException {
    dao.insert();
    throw new IOException();   // insert 仍留在資料庫
}
```

**解題思路**

1. 先確認呼叫有沒有跨過代理（第 1 篇）。
2. **檢查方法可見度（public / private / final）：替身要攔得到方法才會開交易（本篇）。**
3. **檢查例外是不是被自己吃掉：替身看例外有沒有穿出來決定 commit 或 rollback（本篇）。**
4. **檢查是不是 checked 例外：預設回滾規則只含 RuntimeException 與 Error（本篇）。**
5. 最後談修法。

**答案**

三種都出在替身看不到、或看不出要回滾。方法用 public，例外要穿出方法，checked 例外用 rollbackFor 明講。

```java
// 解法 A：改成 public
@Transactional
public void saveA() { dao.insert(); }

// 解法 B：記完 log 再丟出去
@Transactional
public void saveB() {
    try {
        dao.insert();
        dao.update();
    } catch (RuntimeException e) {
        log.error(e);
        throw e;               // 替身才會 rollback
    }
}
// 替代：TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();

// 解法 C：明講 checked 例外也要回滾
@Transactional(rollbackFor = Exception.class)
public void saveC() throws IOException {
    dao.insert();
    throw new IOException();
}
```

### 第 1 輪 · 釐清：Spring 的替身到底是靠什麼判斷「這次要 commit 還是 rollback」？

```java
// 簡化示意（不是 Spring 原始碼）
public Object invoke(Method m, Object[] args) throws Throwable {
    if (!替身攔得到(m)) {
        return m.invoke(target, args);   // 情況 A：沒交易
    }
    tx.begin();
    try {
        Object r = m.invoke(target, args);
        tx.commit();                     // 情況 B：例外被吃掉 = 正常結束 = commit
        return r;
    } catch (Throwable ex) {
        if (ex instanceof RuntimeException || ex instanceof Error) {
            tx.rollback();               // 預設只有這兩類回滾
        } else {
            tx.commit();                 // 情況 C：checked 例外照樣 commit
        }
        throw ex;                        // 仍丟給呼叫者，所以看得到報錯卻沒回滾
    }
}
```

### 第 2 輪 · 挑戰假設：方法只要不是 public，@Transactional 就一定失效嗎？

```java
@Transactional private void a() {}          // 永遠失效：子類別看不到 private
@Transactional protected void b() {}        // Spring 5（Boot 2）以前失效；Spring 6（Boot 3）class 型代理下有效
@Transactional void c() {}                  // package-private，同 b
@Transactional public final void d() {}     // 失效：final 不能被覆寫
// 介面型代理（JDK proxy）只認介面上宣告的 public 方法
// 驗證：方法第一行印 TransactionSynchronizationManager.isActualTransactionActive()，false 就是沒交易
```

### 第 3 輪 · 追原因：為什麼預設只有 RuntimeException 才回滾，checked 例外不是一起回滾？

```java
// RuntimeException / Error：程式 bug 或系統壞掉，沒人預期 → 預設回滾
// checked 例外：業務上可預期、呼叫者可處理 → 預設不回滾，交給你決定
class InsufficientBalanceException extends Exception {}

@Transactional
public void withdraw() throws InsufficientBalanceException {
    dao.deductFee();
    if (餘額不足) {
        throw new InsufficientBalanceException();   // 預設：手續費已 commit
    }
}

@Transactional(rollbackFor = InsufficientBalanceException.class)   // 或 Exception.class
// 反過來：@Transactional(noRollbackFor = SomeRuntimeException.class)
```

### 追問：同類內部呼叫失效，那要怎麼解？

```java
// 做法一（最乾淨）：搬到另一個 Bean，從外面呼叫
@Service
class OrderService {
    private final OrderWriter writer;
    public void process() { writer.save(); }   // 跨過 Bean 邊界
}
@Service
class OrderWriter {
    @Transactional
    public void save() { dao.insert(); }
}

// 做法二：注入自己，用注入進來的替身呼叫（能動但不好看）
@Service
class OrderService {
    @Lazy @Autowired
    private OrderService self;   // @Lazy：Boot 2.6 起預設禁止循環相依
    public void process() { self.save(); }
    @Transactional
    public void save() { dao.insert(); }
}

// 做法三：TransactionTemplate 手動控制
@Service
class OrderService {
    private final TransactionTemplate tx;
    public void process() {
        tx.executeWithoutResult(status -> {
            dao.insert();
            dao.update();    // RuntimeException 回滾；也可 status.setRollbackOnly()
        });
    }
}
```

### 為什麼要懂

呼叫外部 API 失敗丟了 IOException，log 有錯，資料庫卻留著半筆資料，對帳對不起來。不知道 checked 例外預設不回滾、或 try-catch 會讓替身以為一切正常，就會一直查錯方向。

### 結論

替身只看兩件事：攔不攔得到方法、例外有沒有穿出來而且是 RuntimeException 或 Error。檢查順序：看可見度、看例外、看 rollbackFor。

官方文件：https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html

### 術語表

| 術語 | 白話定義 |
|---|---|
| 代理（替身） | Spring 包在 Bean 外面的一層，負責在方法前後開交易、commit 或 rollback |
| 回滾 rollback | 把交易內已做的資料庫修改全部撤銷 |
| checked 例外 | 編譯器強迫 try-catch 或寫 throws 的例外，如 IOException |
| CGLIB | 用產生子類別做替身的方式，所以 private、final 覆寫不了 |
| rollbackFor | @Transactional 的屬性，指定哪些例外要回滾 |
| setRollbackOnly | 手動標記這筆交易只能回滾，不必丟例外 |
| TransactionTemplate | 用程式碼手動把一段邏輯包進交易，不靠註解 |
