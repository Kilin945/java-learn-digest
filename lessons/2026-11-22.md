## A5 第 1 篇 · 同類內部呼叫（self-invocation）為什麼不會觸發 @Transactional

**題目：@Transactional 什麼時候會失效？**

### 題目在問什麼

- @Transactional：標在方法上的記號，意思是「請把這個方法包在一次資料庫交易裡」，成功一起存、出錯全部撤銷（回滾）。
- 「失效」：標了但沒開交易、也沒回滾，而且不報錯。
- 要答到：失效有哪幾種、各自為什麼。本篇只講同類內部呼叫。

```java
// 題目拆解（簡化示意）
@Service
public class OrderService {

    public void a() {      // 外面呼叫 a()；a 沒有標 @Transactional
        b();               // a 呼叫同一個類別裡的 b
    }

    @Transactional
    public void b() {
        // 先寫一筆資料進資料庫
        throw new RuntimeException("出錯");
    }
}
// 直覺預期：b 出錯 → 回滾
// 實際：從 a() 進來 → 沒開交易 → 資料已存入，沒有回滾、沒有警告
```

### 解題思路

1. 要知道「什麼時候失效」，先知道生效靠什麼：替身（proxy）替你開交易。
2. **最常見的失效：呼叫沒經過替身。同類內部呼叫就是（本篇）。**
3. 其他失效情況：非 public、例外被吃掉、checked 例外預設不回滾（第 2 篇）。
4. 怎麼解（第 2 篇）。

### 答案

同一個類別裡 a() 呼叫 b() 其實是 this.b()，this 是真物件而不是替身，替身沒機會開交易，所以 b 上的 @Transactional 被略過。

```java
// 簡化示意：Spring 替 OrderService 做的替身
class OrderServiceProxy extends OrderService {
    OrderService target;                // 被包在裡面的真物件

    public void a() { target.a(); }     // a 沒標記 → 直接轉給真物件

    public void b() {                   // b 有標記 → 前後加料
        開交易();
        try { target.b(); 提交(); }
        catch (RuntimeException e) { 回滾(); throw e; }
    }
}
// 路線 1：Controller → proxy.b() → 開交易 → target.b()   有交易
// 路線 2：Controller → proxy.a() → target.a() → this.b()  沒交易
//   target.a() 裡的 this 是真物件，this.b() 直接進真的 b
```

### 第 1 輪 · 釐清：方法裡的 this 到底是誰？

```java
// 簡化示意
@Service
public class OrderService {
    public void a() {
        System.out.println(this.getClass());   // OrderService（真物件）
        b();                                   // 等同 this.b()
    }
}
// orderService.getClass() → OrderService$$SpringCGLIB$$0 （替身）
// this.getClass()         → OrderService                 （真物件）
// 真物件不知道外面包了替身，呼叫自己只會走到自己
```

### 第 2 輪 · 換視角：為什麼不讓 this 指向替身？

```java
// 替身是從外面包住，不是改寫真物件
//   呼叫端 ──▶ 替身 ──▶ 真物件
// this 是 Java 語言規定的「自己這個物件」，Spring 改不了
//
// AspectJ 織入模式（簡化示意，需要 spring-aspects）
@EnableTransactionManagement(mode = AdviceMode.ASPECTJ)
// 直接改寫編譯後的 class，this.b() 也攔得到
// 預設 PROXY 模式：簡單，代價是內部呼叫攔不到
```

### 第 3 輪 · 連結經驗：怎麼在自己的 code 裡驗證？

```java
// 典型寫法（簡化）：暫時加在要驗證的 @Transactional 方法裡
@Transactional
public void b() {
    boolean active =
        TransactionSynchronizationManager.isActualTransactionActive();
    System.out.println("有交易嗎？ " + active);
}
// 實驗 1：別的 Bean 呼叫 service.b()   → true
// 實驗 2：同類的 a() 呼叫 b()           → false
// （a 自己也標 @Transactional 時會是 true，但那是 a 開的交易，b 的設定如 REQUIRES_NEW 仍被略過）
//
// 不改程式：application.properties
//   logging.level.org.springframework.transaction.interceptor=TRACE
// 有經過替身 → 出現 Getting transaction for [...b]；內部呼叫 → 沒有
```

### 為什麼要懂

把要存兩張表的邏輯抽成同類小方法並標上 @Transactional，測試正常，上線後某次出錯卻留下半套資料。因為不報錯，只能先懷疑內部呼叫略過交易，再用對照實驗確認。

### 結論

@Transactional 靠替身才生效，同類內部呼叫走 this 繞過替身，所以標記被略過。判斷方式：看這次呼叫有沒有從 Bean 外面進來。

深入官方文件：[Spring Framework：Proxying Mechanisms](https://docs.spring.io/spring-framework/reference/core/aop/proxying.html)

### 術語表

| 術語 | 白話定義 |
|---|---|
| self-invocation | 同一個類別裡一個方法呼叫自己類別的另一個方法（等於 this.xxx()） |
| 交易（transaction） | 一組資料庫操作，要嘛全部成功、要嘛全部撤銷 |
| 回滾（rollback） | 交易中途出錯時，把已寫入的變更全部撤銷 |
| 代理／替身（proxy） | Spring 包在真物件外面的一層物件，在方法前後加交易等動作 |
| this | Java 裡「目前這個物件自己」，在真物件方法裡就是真物件 |
| 織入（weaving） | 直接把額外邏輯寫進編譯後的 class，不靠替身（AspectJ） |
