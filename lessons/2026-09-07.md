## 交易：@Transactional 的邊界與陷阱 · 第 4 步

### 概念：Caught Exceptions Don't Trigger Rollback（吞掉例外 = 不會 rollback）

@Transactional 的角色像站在方法門口的保全，只有聽到「例外從方法裡跑出去」這件事，他才會啟動 rollback（回復原狀）。

如果方法內部用 try-catch 把例外攔住，只做 log 記錄卻沒有把例外重新拋出（rethrow），Spring 完全偵測不到任何錯誤，方法會被視為「正常結束」，交易照樣 commit（送出、定案）——即使資料其實已經壞掉一半。

### 程式碼：踩坑寫法

```java
@Transactional
public void placeOrder(Order order) {
    try {
        orderRepository.save(order);
        paymentService.charge(order); // 這裡丟出 RuntimeException
    } catch (Exception e) {
        log.error("下單失敗", e); // 只記 log，沒有 rethrow
    }
    // 方法正常結束，Spring 認為一切 OK，直接 commit！
    // 結果：訂單存了，但錢沒扣到，資料庫壞掉一半
}
```

### 術語表

| 術語 | 中文 | 定義 |
|---|---|---|
| try-catch | 例外攔截 | Java 語法，攔住可能發生的例外，避免程式直接崩潰 |
| rethrow | 重新拋出 | 在 catch 區塊用 `throw e;` 把例外再丟出去，讓外面（含 Spring 代理人）知道出事 |
| swallow exception | 吞掉例外 | 攔到例外後沒有處理也沒有重新拋出，錯誤訊息消失 |

### 一句話帶走

例外只有「真的往外丟出方法」才算數，自己 catch 住卻不重新拋出，等於跟 Spring 說「沒事，可以 commit」。
