## A4 第 1 篇 · 沒有 AOP 時：交易、log、權限檢查在每個方法重複寫

### ⭐ AOP 是什麼？Spring 怎麼實作？

**題目在問什麼**

- AOP 是 Aspect-Oriented Programming，切面導向程式設計。它是一種做法，不是 Spring 專屬。
- 要答完兩件事：① AOP 是什麼、解決什麼問題（本篇）；② Spring 怎麼做到：動態代理（第 2 篇）。

```java
// 要交出的東西 = 回答兩件事：
//   ① 它是什麼？把「每個方法都要做、但不是業務本身」的事抽出來統一管  ← 本篇
//   ② Spring 怎麼做到？動態代理                                        ← 第 2 篇
```

**解題思路**

1. 先看沒有 AOP 時，一個方法裡混了哪些東西（本篇）
2. 再看重複寫會壞在哪（本篇）
3. AOP 的做法：把重複的抽成一份統一套用（本篇結尾一句帶過）
4. Spring 怎麼實作：動態代理（第 2 篇）
5. 追問：self-invocation（第 2 篇）

**答案**

沒有 AOP 時，每個業務方法都得自己手寫權限檢查、log、開交易、commit/rollback，這些重複的事就叫橫切邏輯。AOP 就是把它們從業務方法抽走、集中管理。

```java
// 典型寫法（簡化示意）：沒有 AOP，轉帳方法自己手寫所有事
public void transfer(String from, String to, int amount) throws Exception {
    // 橫切①：權限檢查
    if (!currentUser.hasRole("SUPERVISOR")) {
        throw new AccessDeniedException("no permission");
    }
    // 橫切②：記 log（開始）
    log.info("transfer start: " + from + " -> " + to);
    // 橫切③：手動開交易
    Connection conn = dataSource.getConnection();
    conn.setAutoCommit(false);   // 關掉自動提交，等我說 commit 才生效
    try {
        // ★ 真正的業務只有這兩行
        accountDao.withdraw(conn, from, amount);
        accountDao.deposit(conn, to, amount);
        conn.commit();
        log.info("transfer ok");
    } catch (Exception e) {
        conn.rollback();
        log.error("transfer fail", e);
        throw e;
    } finally {
        conn.close();
    }
}
// 約 25 行，業務只有 2 行，其餘全是橫切
```

### 第 1 輪 · 釐清：「橫切邏輯」到底是什麼？跟業務邏輯要怎麼分？

```java
// 業務邏輯：方法存在的理由（轉帳 = 扣款 + 入帳）
// 橫切邏輯：橫著切過很多類別、方法；每個都要，但都不是本業
class TransferService {
    void transfer() {
        權限檢查();  記log();  開交易();    // 橫切
        扣款();      入帳();               // 業務
        commitOrRollback();  記log();      // 橫切
    }
}
class OrderService {
    void cancel() {
        權限檢查();  記log();  開交易();    // 橫切（複製貼上）
        取消訂單();                        // 業務
        commitOrRollback();  記log();      // 橫切
    }
}
// 判斷口訣：換一個類別、一個方法，這段還是長得一樣 → 橫切
```

### 第 2 輪 · 反事實：如果每個方法都自己手寫權限、log、交易，會壞在哪？

```java
// 壞法①：漏寫（簡化示意）
public void closeAccount(String id) throws Exception {
    // 忘了權限檢查 → 任何登入的人都能關帳戶（越權）
    Connection conn = dataSource.getConnection();
    conn.setAutoCommit(false);
    try {
        accountDao.markClosed(conn, id);
        auditDao.insert(conn, id);      // 這行丟例外
        conn.commit();
    } catch (Exception e) {
        // 忘了 conn.rollback() → 交易沒被明確還原，狀態不確定
        throw e;
    }
}
// 壞法②：改規則要改 N 處（例如 log 要多帶 traceId）
// 壞法③：業務被淹沒，code review 時眼睛都在看樣板
```

### 第 3 輪 · 連結經驗：我專案裡的 @Transactional、@Secured（Supervisor 角色授權）對應手寫版哪幾行？

```java
// 典型寫法（簡化）；角色名稱 ROLE_SUPERVISOR 是示範，以實際專案為準
@Transactional                    // 取代：setAutoCommit(false) / commit / rollback / close
@Secured("ROLE_SUPERVISOR")       // 取代：if (!hasRole(...)) throw ...
public void transfer(String from, String to, int amount) {
    accountDao.withdraw(from, amount);
    accountDao.deposit(to, amount);
}
// 被取代的行改由「別人」在方法前後自動補上，是誰、怎麼補 → 第 2 篇（動態代理）
```

**為什麼要懂**

某天某個方法的交易沒生效、或權限檢查被繞過，卻不知道註解背後原本替你做了什麼。先知道手寫版有哪些行，才看得懂「註解沒生效」少掉的是哪一段。

**結論**

AOP 要解決的是：交易、log、權限這類每個方法都要、卻不是業務本身的程式碼，不該在每個方法裡重複手寫。把它們抽成一份統一套用，業務方法就只剩業務。

### 📖 術語表

| 術語 | 白話定義 |
|---|---|
| AOP | Aspect-Oriented Programming，切面導向程式設計。把橫切邏輯從業務方法抽出來集中管理的做法 |
| 橫切邏輯 | cross-cutting concern。很多方法都要、但不是本業的事，如交易、log、權限檢查 |
| 業務邏輯 | 方法存在的理由，例如轉帳的扣款與入帳 |
| 交易（transaction） | 一組要嘛全成功、要嘛全還原的資料庫操作；成功叫 commit，還原叫 rollback |
| 越權 | 沒資格的人做了該有資格才能做的事 |
| 動態代理 | 執行時產生、包在真正物件外面的替身物件（第 2 篇講） |
