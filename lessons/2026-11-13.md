## B4 第 3 篇 · 怎麼查 OOM：HeapDumpOnOutOfMemoryError、heap dump 怎麼讀、Metaspace vs heap OOM

**題目**：JVM 記憶體區與 OOM 常見成因？

### 題目在問什麼
- OOM = OutOfMemoryError，訊息冒號後面說明哪一區爆。
- heap dump = 某一刻 heap 內全部物件的快照（.hprof）。
- 要答完：①怎麼自動留 dump ②dump 怎麼讀 ③Metaspace 與 heap 差別。

```text
java.lang.OutOfMemoryError: Java heap space   // 堆滿了
java.lang.OutOfMemoryError: Metaspace         // 類別資訊區滿了
```

### 解題思路
1. 看 log 判斷哪一區爆（第 1 篇）
2. **事先開好自動 dump（本篇）**
3. **用工具依誰佔最多排序、追被誰參照（本篇）**
4. **分辨 Metaspace 與 heap（本篇）**
5. 找出被抓著不放的成因（第 2 篇）

### 答案
啟動參數加 `-XX:+HeapDumpOnOutOfMemoryError`，並用 `-XX:HeapDumpPath` 指定位置，炸的當下自動寫出 .hprof，事後用 Eclipse MAT 看誰佔最多、被誰參照。

```bash
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dumps/ -jar app.jar
export JAVA_TOOL_OPTIONS='-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dumps/'
```

### 第 1 輪（釐清）：Shallow Heap、Retained Heap、Dominator Tree 是什麼？
```java
class Cache { Map<String, byte[]> map = new HashMap<>(); }
// Shallow：物件自己的大小（Cache 很小）
// Retained：回收它後連帶能釋放的總大小（Cache 很大）
// Dominator Tree：依 Retained 由大到小排，第一名是頭號嫌疑
// 不要用 Shallow 排名找兇手：byte[]、String 只是被抓著的東西
```
MAT 操作順序：Leak Suspects Report → Histogram → Dominator Tree → 右鍵 Path to GC Roots（exclude weak/soft references）。

### 第 2 輪（反事實）：沒開 HeapDumpOnOutOfMemoryError 會壞在哪？
- OOM 後服務重啟，heap 清空，證據消失；只剩 log 一行訊息。
- 手動補救：`jcmd <pid> GC.heap_dump /data/dumps/manual.hprof`，要在問題發生當下拍，拍的時候程式暫停，預設先 Full GC、只存活物件。

### 第 3 輪（挑戰假設）：開了參數，dump 一定留得下來嗎？
- 磁碟放不下（大小約等於 heap 使用量）
- 路徑無寫入權限或不存在
- 放在容器內部，重啟即消失，需掛外部 volume
- 死因是作業系統 OOM Killer，JVM 來不及丟 OOM，不會觸發
- dump 內含敏感資料，需謹慎處理

### 追問：Metaspace OOM 跟 heap OOM 差在哪？怎麼開 HeapDumpOnOutOfMemoryError？
| | heap OOM | Metaspace OOM |
|---|---|---|
| 訊息 | Java heap space | Metaspace |
| 放什麼 | 物件 | 類別資訊 |
| 上限參數 | -Xmx | -XX:MaxMetaspaceSize（沒設幾乎不限，吃原生記憶體） |
| 典型成因 | 該回收的被抓著、快取沒上限 | 反覆熱部署、動態產生類別 |
| 症狀 | 隨資料量、流量長大 | 重啟後好一陣子又爆 |
| 查法 | dump → Dominator Tree | jcmd 看 ClassLoader 與類別數量 |

```bash
jcmd <pid> VM.classloader_stats
jcmd <pid> GC.class_histogram
```
舊的 ClassLoader 若被抓著，它載入的類別就卸載不掉；原理與 heap 相同，都是被抓著不放。-XX:+HeapDumpOnOutOfMemoryError 對任何 OutOfMemoryError 都會觸發；調大 MaxMetaspaceSize 只是延後，不是修好。

### 為什麼要懂
半夜服務掛了而沒開自動 dump，隔天只剩一行 log 查不下去；把 Metaspace 爆誤當 heap 爆，調大 -Xmx 也沒用。

### 結論
先看 log 判斷哪一區爆，事先開自動 dump 留現場，用 MAT 的 Dominator Tree 與 Path to GC Roots 找出誰抓著不放。heap 爆是物件，Metaspace 爆是類別。

### 術語表
- OOM：OutOfMemoryError，要不到記憶體時丟出的錯誤
- heap dump / .hprof：某一刻 heap 全部物件的快照檔
- Eclipse MAT：打開 heap dump 的分析工具
- Shallow / Retained Heap：物件自己的大小／回收後連帶釋放的總大小
- Dominator Tree：依 Retained Heap 排序的物件樹
- GC Root：GC 判斷還在用的起點
- Metaspace：放類別資訊的原生記憶體區
- ClassLoader：載入類別的物件
- jcmd：JDK 內建、對執行中 JVM 下命令的工具
