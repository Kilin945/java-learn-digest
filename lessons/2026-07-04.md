## @Autowired、@Qualifier 與多個候選 Bean 的解析 · 第 2 步

### 概念：Too Many Candidates（候選人太多）

昨天學到只有一個實作類別時，`@Autowired` 能順利把 Bean 注入建構子。今天打破這個假設：當同一個介面（interface）有**兩個以上**的實作類別（implementation）時，Spring 找不到唯一答案，會直接拋出 `NoUniqueBeanDefinitionException`。

比喻：城裡只有一家披薩店時，外送員理所當然知道去哪拿貨；但有兩家披薩店都能送「披薩」時，外送員會愣住、拒絕出發——這就是 Spring 遇到多個候選 Bean 時的反應。

### 問題程式碼

```java
// 介面：定義「發通知」這個服務長什麼樣子
public interface NotificationService {
    void send(String message);
}

// 實作類別一
@Service
public class EmailNotificationService implements NotificationService {
    public void send(String message) {
        System.out.println("寄 Email: " + message);
    }
}

// 實作類別二
@Service
public class SmsNotificationService implements NotificationService {
    public void send(String message) {
        System.out.println("發簡訊: " + message);
    }
}

// 這裡出事了！Spring 不知道要塞哪一個進來
@Component
public class OrderProcessor {

    private final NotificationService notificationService;

    @Autowired
    public OrderProcessor(NotificationService notificationService) {
        this.notificationService = notificationService;
    }
}

// 啟動時的錯誤訊息：
// NoUniqueBeanDefinitionException: expected single matching bean
// but found 2: emailNotificationService, smsNotificationService
```

> 這個「壞掉」的版本會留到明天，用 `@Qualifier` 修好它。

### 術語表

| 術語 | 定義 |
|---|---|
| Interface（介面） | 只定義有哪些方法，不寫實際做法的規格書 |
| Implementation（實作類別） | 真正把介面內容寫出來的具體類別 |
| Bean（元件） | 被 Spring 容器建立與管理的物件 |
| NoUniqueBeanDefinitionException | Spring 找到多個符合條件的候選 Bean，無法自動決定要注入哪一個時拋出的例外 |

### 昨日複習
1. @Autowired 標在建構子上，告訴 Spring 要準備哪些依賴並送進來。
2. 依賴注入（DI）讓類別不用自己 new 依賴物件，改由外部容器準備並送入，降低耦合。
3. 因為只有一個實作類別時，Spring 找候選人只找到一個，不需選擇即可直接注入。
